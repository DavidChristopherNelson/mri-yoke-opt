# Rent sixteen EPYC cores, parallelize variants

The best way to run this workload faster is a single 16-32-physical-core x86 AMD EPYC (Genoa or Turin) Linux VM bought on spot in a US-East region, with per-iteration checkpoints to a bucket, and one such VM per design variant. Today that costs about **$0.19-0.25 per hour for 16 real cores** (AWS c8a/c7a in us-east-2, Azure Falsv7 in eastus/eastus2), so a "10 h x 16 cores" session is roughly **$2 on spot and $8-10 on demand**, and 600 h/month is roughly **$110-150 on spot**. The expected speedup over the 6-core i7 laptop is **about 4-8x per run** (an inference from memory-bandwidth and single-thread ratios, not a measured NGSolve result), so a 4-6 h run should drop to roughly an hour; nobody has published NGSolve thread-scaling curves, so a one-dollar calibration run is the first step. The pip wheels decide the hardware: there is no Linux ARM wheel, MKL Pardiso exists only on x86-64, MUMPS and hypre are compiled out, and NUMA support is off, which rules out Graviton/Ampere/Axion and favors a single-socket slice. More cores than about 32 will not help the current 263k-dof problem; the large win beyond one fast node is running several variants side by side, which scales perfectly. MPI, GPU and managed PaaS products (Railway, Fly.io) are the wrong tools here; Modal and Oracle are the sensible fallbacks when spot quota or interruptions get in the way.

## NGSolve scales by threads on one x86 node, and the wheels pick the hardware

NGSolve's shared-memory parallelism is a task-stealing thread pool. The documentation lists what it parallelizes: finite element assembly (by element coloring), sparse matrix graph creation, matrix-vector products, vector updates and inner products; the thread count defaults to the number of logical cores and is overridden with `NGS_NUM_THREADS` or `SetNumThreads(n)` ([NGSolve parallel how-to](https://docu.ngsolve.org/latest/how_to/howto_parallel.html)). That covers the bulk of this job's Newton loop (assembly plus CG), but **no published strong-scaling tables for TaskManager, BDDC setup or the in-house sparse Cholesky were found** in the docs or forum. The only field evidence is cautionary: a 2022 forum case on a 16-core AMD laptop ran a small eigenproblem in 1.7 s with TaskManager versus 0.9 s without, and the lead developer explained that `sparsecholesky` "works together with TaskManager" while UMFPACK and Pardiso "do their own threading, and compete against TaskManager" ([NGSolve forum](https://forum.ngsolve.org/t/bad-taskmanager-performance-for-eigenvalue-problems/2030)). Inspection of the current wheel shows the Pardiso wrapper now imports `SuspendTaskManager` and sets MKL's local thread count, which suggests that conflict has been addressed, but this was not confirmed by execution ([PyPI ngsolve 6.2.2608](https://pypi.org/project/ngsolve/6.2.2608/#files)).

The packaging facts are firmer and matter more. Wheels for ngsolve 6.2.2608 (uploaded 2026-10-01) exist only for **manylinux_2_28 x86_64, macOS universal2 and Windows amd64; there is no Linux aarch64 wheel and no sdist** ([PyPI ngsolve files](https://pypi.org/project/ngsolve/6.2.2608/#files)). The Linux wheel is built with UMFPACK on and MKL, Pardiso, MUMPS and hypre off; `sparsecholesky` is always present, and `pardiso` becomes available at runtime when the pip `mkl` package is installed, which itself ships only for x86-64 Linux and Windows ([PyPI mkl](https://pypi.org/project/mkl/#files)). So on a Linux x86 cloud VM the direct solvers are sparsecholesky, UMFPACK and (after `pip install mkl`) Pardiso; on the Mac they are sparsecholesky, UMFPACK and Apple's Accelerate Sparse, with no Pardiso. The Netgen wheel is compiled with `-march=core-avx2` and `USE_NUMA=OFF` ([PyPI netgen-mesher files](https://pypi.org/project/netgen-mesher/6.2.2608/#files)): any AVX2 CPU works, AVX-512 is unused, and a two-socket machine gets no NUMA-aware placement, so a single-socket slice (or `numactl`) is the safe choice. That last point is an inference, not a documented NGSolve recommendation.

MPI is technically available but not worth the restructuring. The Linux wheels are built with `USE_MPI=ON` through an MPICH/OpenMPI wrapper, and the docs list BDDC and MUMPS as MPI-capable, but MUMPS is not in the wheel, mesh generation, adaptive refinement, multigrid and pickling are unsupported under MPI, and the mesh must be generated on rank 0 and distributed ([NGSolve parallel how-to](https://docu.ngsolve.org/latest/how_to/howto_parallel.html); [MPI tutorial](https://docu.ngsolve.org/latest/i-tutorials/unit-5a.1-mpi/poisson_mpi.html)). A scalable distributed direct solve or hypre AMS means building PETSc with MUMPS/hypre and using ngsPETSc, since petsc4py is sdist-only ([forum: MUMPS with pip](https://forum.ngsolve.org/t/make-mumps-and-others-solvers-available-on-ngsolve-install-with-pip/2907); [ngsPETSc](https://github.com/NGSolve/ngsPETSc)). No source demonstrates an MPI advantage over threads at 0.26M-10M dofs, and the eleven-adjoint-solves-per-matrix pattern favors one shared-memory factorization or preconditioner reused many times. GPU offload is similarly premature: the `ngsolve.gpu` layer was redesigned and announced on 2026-09-09, the tutorial covers Poisson only, and nothing documents HCurl use ([forum announcement](https://forum.ngsolve.org/t/gpu-support-for-cuda-and-metal/3880); [GPU tutorial](https://docu.ngsolve.org/latest/i-tutorials/unit-5.6-gpu/poisson_gpu.html)).

## Memory channels, not core counts, set a realistic 4-8x speedup

Sparse iterative FEM is bounded by memory bandwidth. A 2026 analysis of 175 OpenFOAM runs across 25 CPU models concludes that "within a single node, performance is bounded by memory bandwidth", that large caches show no particular trend once data dwarfs them, and that on-package high-bandwidth memory dominates single-node results ([arXiv 2603.27565](https://arxiv.org/pdf/2603.27565)). The laptop's i7-9750H has two DDR4-2666 channels and a **41.8 GB/s** theoretical ceiling ([WikiChip](https://en.wikichip.org/wiki/i7-9750H)); a Sapphire Rapids socket offers about 307 GB/s and an EPYC Genoa socket about **461 GB/s** across 12 DDR5 channels ([The Next Platform](https://www.nextplatform.com/2023/06/12/intel-pits-its-sapphire-rapids-xeon-sp-against-amd-genoa-epycs/)), and Azure measured up to 780 GB/s STREAM triad on its two-socket Genoa-X HBv4 node ([Azure HPC blog mirror](https://thewindowsupdate.com/2023/06/13/performance-scalability-of-hbv4-and-hx-series-vms-with-genoa-x-cpus/)). A desktop Ryzen 9 9950X manages only 96 GB/s theoretical ([Chips and Cheese](https://chipsandcheese.com/p/amds-ryzen-9950x-zen-5-on-desktop)), which is why "fast desktop chip by the hour" offers (Ryzen and EPYC 4004/4005 bare metal) are the wrong class despite their roughly 2x single-thread advantage over the laptop ([PassMark](https://www.cpubenchmark.net/compare/3425vs6211vs5031vs6345/Intel-i7-9750H-vs-AMD-Ryzen-9-9950X-vs-AMD-EPYC-9654-vs-Apple-M4-Max-16-Core)). A forum-grade rule of thumb puts saturation at 2-4 cores per memory channel ([cfd-online](https://cfd-online.com/Forums/hardware/224528-epyc-7302-scalability.html)); the laptop sits at 3 cores per channel already, while a 16-32-core slice of a 12-channel EPYC is core-limited rather than bandwidth-limited, provided neighbours on the shared socket are quiet.

The speedup figures that follow are **estimates assembled from those ratios, not measurements**; no benchmark of NGSolve or any FEM code on the i7-9750H versus current server CPUs was found. For 16-32 Genoa or Turin cores the notes estimate 5-10x on the memory-bound solve phase and **4-8x on the whole job** once serial Python and level-set steps (which gain only the roughly 1.3-2x single-thread ratio) are included. A whole Genoa-X HPC node lands at 4-10x for the current problem and 10-20x or more only for multi-million-dof runs that can use 48-96 cores. Sustained laptop load also throttles: forum reports put the 45 W i7-9750H near 3.0 GHz under long all-core load ([TechPowerUp forum](https://www.techpowerup.com/forums/threads/i7-9750h-isnt-using-turbo-anymore.267797/)), so the cloud gain on compute-bound sections is somewhat larger than benchmark databases imply. The 263k-dof problem is small enough that thread overhead probably caps useful threads at 8-16; buying more than 32 cores for one run is wasted until the mesh grows.

Three CPU traits therefore matter, in order: physical cores with SMT off (one thread per core for bandwidth-bound kernels), memory channels per core, and x86-64 for MKL Pardiso. V-Cache helped OpenFOAM and Fluent by up to 1.49x and 1.42x over plain Genoa in Azure's tests ([Azure HPC blog mirror](https://thewindowsupdate.com/2023/06/13/performance-scalability-of-hbv4-and-hx-series-vms-with-genoa-x-cpus/)) and could suit the current cache-sized problem, but that is unverified for NGSolve. For the later order-3, multi-million-element target the solver strategy changes more than the hardware: 3D nested-dissection factorization costs O(N^2) time and O(N^(4/3)) memory ([arXiv 2511.07773](https://arxiv.org/pdf/2511.07773)), so going from 0.3M to 5M dofs multiplies factor memory by about 43 and factor time by about 280. Direct solves stop being viable; BDDC-preconditioned CG with O(N) memory becomes the only path, and memory bandwidth plus 128-768 GB of RAM become the governing specs.

## Deployment is pip on Ubuntu plus a checkpoint, and parallel variants are the real multiplier

The install is the same `pip install ngsolve` used on the laptop. The wheel needs glibc 2.28 or newer and Python 3.10-3.14 ([PyPI ngsolve files](https://pypi.org/project/ngsolve/6.2.2608/#files)), which Ubuntu 22.04/24.04 or a `python:3.12-slim` image satisfy; add `pip install mkl` if Pardiso is wanted. The Netgen wheel is built with the GUI enabled and bundles some X/GLU libraries ([PyPI netgen-mesher files](https://pypi.org/project/netgen-mesher/6.2.2608/#files)), so installing `libgl1` and basic X libraries in a headless container is a sensible precaution; whether the import actually fails without them is unverified. No current official Docker image or conda package was confirmed, so a five-line Dockerfile on a slim Python base, or a bare VM with a venv, is the practical route. Set `NGS_NUM_THREADS` to the physical core count, test `OPENBLAS_NUM_THREADS=1` (the wheel bundles a pthreads OpenBLAS that can oversubscribe inside TaskManager regions; unverified), keep the process on one socket, and profile one iteration with `TaskManager(pajetrace=10**8)` to see which phases actually scale ([TaskManager tutorial](https://docu.ngsolve.org/latest/i-tutorials/appendix-taskmanager/taskmanager.html)).

Spot requires checkpoint/restart, and this optimizer is already close: 150-250 sequential iterations with a level-set field and history that are written to disk map naturally onto "save state every iteration, resume from the last one". Notice periods are short: two minutes on AWS, best-effort up to 30 seconds on GCP and Azure ([GCP preemptible docs](https://docs.cloud.google.com/compute/docs/instances/preemptible); [Azure Spot docs](https://learn.microsoft.com/en-us/azure/virtual-machines/spot-vms)), so checkpointing on a per-iteration cadence rather than on the signal is the robust design. With iterations expected to take 10-30 seconds on the cloud node, an interruption costs at most one iteration plus a reboot. Writing checkpoints and outputs to object storage makes the VM disposable; at a few GB per run storage and egress are negligible.

For launching, three layers fit. SkyPilot managed jobs provision a temporary cluster per job and "handle auto-recovery" from spot preemption across AWS, GCP and Azure, at the price of a YAML file and a small controller ([SkyPilot overview](https://docs.skypilot.ai/en/latest/overview.html)). Coiled Batch runs scripts in the user's own cloud account and is reportedly free up to 10,000 CPU-hours per month, a figure taken from a search summary and unverified ([Coiled pricing](https://www.coiled.io/pricing)). Modal needs no cloud account at all: CPU is billed per physical core per second, containers can run up to 24 hours, the Starter plan includes $30/month of credit, and `map`-style fan-out launches one container per variant ([Modal pricing](https://modal.com/pricing); [Modal timeouts](https://modal.com/docs/guide/timeouts)). Its listed rate is the preemptible one and non-preemptible execution costs 3x, so Modal runs about five times AWS spot per core; its maximum cores per container and CPU model are not documented.

The embarrassingly parallel win deserves emphasis. One run is inherently sequential and will gain perhaps 4-8x from better hardware; eight design variants on eight 16-core spot VMs finish in the same wall-clock hour for about $2 total, a throughput gain of 30-60x over running them back to back on the laptop. Because the 263k-dof problem likely stops scaling near 8-16 threads, packing several 16-core jobs onto one large VM or HPC node (each pinned to its own core range) is as efficient as separate VMs and unlocks the cheapest whole-node prices.

## A run costs cents; quotas and account friction cost days

Applying the estimated 4-8x speedup, a current 4-6 h laptop run becomes roughly 0.5-1.5 h on 16 cloud cores: about **$0.10-0.35 on AWS or Azure spot and $0.45-1.45 on demand** (computed from the table; the speedup is an estimate). The requested reference points are firmer: 10 h x 16 cores costs $1.80-2.50 on AWS/Azure spot, $2.72 on Oracle preemptible, $5.44 on Oracle on demand, $8.20-9.70 on AWS/Azure on demand, about $10 on Modal preemptible or a generic 32-vCPU VPS, and $12.72 on GCP C4D on demand. Heavy use at 600 h/month per 16-core slot costs $107-152 on AWS/Azure spot, $163 on Oracle preemptible, $326 on Oracle on demand, $493-581 on AWS/Azure on demand and about $600 on Modal or Hetzner. Flat monthly bare metal only competes with on-demand, not with spot: the Cherry EPYC 7543 at $209/month for 32 older cores is the lone US offer in the spot price range, and its stock is thin. Budget for a boot disk and a small bucket on top; both are minor.

Sales tax is an open question. AWS is registered to collect sales tax in Massachusetts but publishes no per-service breakdown ([AWS tax help](https://aws.amazon.com/tax-help/united-states/)). Massachusetts taxes prewritten software, including remotely accessed software, at 6.25%; the on-point guidance is Letter Ruling 12-8 on cloud computing, whose text could not be read ([Mass. DOR Letter Ruling 12-8](https://www.mass.gov/letter-ruling/letter-ruling-12-8-cloud-computing)). The working assumption, unverified, is that raw Linux compute carries no Massachusetts sales tax or at worst 6.25%; the first invoice settles it. No Azure or GCP statement on Massachusetts was found.

Credits help a little and quotas hurt a lot. AWS gives new customers $100 at signup plus up to $100 for onboarding activities, with a free plan restricted to select services and a paid plan whose credits last 12 months ([AWS free tier plans](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier-plans.html)); Google Cloud gives $300 for 90 days but trial accounts cannot request quota increases ([Google Cloud free features](https://docs.cloud.google.com/free/docs/free-cloud-features)); Oracle gives $300 for 30 days ([Oracle free tier](https://www.oracle.com/cloud/free/)). Azure's $200/30-day trial and the reported trial caps (GCP 8 vCPU, Azure 4 vCPU) come from secondary sources and are unverified. On AWS, standard on-demand and standard spot vCPU quotas are separate, both documented at a default of 5 vCPU, and the HPC-instance quota defaults to 0 ([AWS EC2 quotas](https://docs.aws.amazon.com/ec2/latest/instancetypes/ec2-instance-quotas.html)). Expect to upgrade to a paid account and file quota requests for 32-64 spot vCPU before the first real run; turnaround is undocumented and community reports range from hours to a few business days. Azure HB/HX and spot quota requests on new subscriptions are reported as frequently refused, which is the main risk to the whole-node option.

## Ranked recommendation

First, **AWS spot in us-east-2 on c8a, c7a or m7a (16-32 cores, one vCPU per core), driven by SkyPilot or a plain launch script with per-iteration checkpoints to S3.** It combines the lowest verified per-core prices with a two-minute interruption notice, published interruption data, several interchangeable instance pools and the simplest quota path. Use m7a/m8a (4 GiB per core) once the mesh grows. Start with a calibration run on a c8a.8xlarge at 1, 4, 8, 16 and 32 threads, comparing sparsecholesky, Pardiso and BDDC-CG; it costs about a dollar and replaces every estimate in this report with a measurement.

Second, **Azure Falsv7/Fasv7 spot in eastus2 or eastus**, a price tie with AWS ($0.011 per core-hour, SMT off, Turin), ranked lower only because eviction rates are opaque and the notice is 30 seconds. Azure becomes first choice for batches of variants if HB120rs_v3 or HB176rs_v4 spot quota is granted: seven to eleven 16-core jobs on one bandwidth-rich node for $0.67-1.33/h.

Third, **Oracle E5/E6 Flex** for work that must not be interrupted: $0.544/h for 16 genuine cores on demand is 35-45% below AWS and Azure on-demand, and the 50%-off preemptible tier is a fixed price rather than a market.

Fourth, **Modal** when setup time matters more than money: no cloud account, quota or image registry, $30/month free credit, built-in fan-out, at roughly $1/h per 16 cores preemptible.

Fifth, **hourly or monthly US bare metal** (Cherry Servers, phoenixNAP, OVH US Scale) only for sustained non-preemptible use above a few hundred hours a month, and only on 8- or 12-channel EPYC/Xeon platforms. GCP ranks below these for this job because its AMD vCPUs are hyperthreads, doubling the effective core price, with regional spot exceptions (C4D in us-west4, C3D in us-south1) whose availability needs checking. Avoid ARM instances (no wheels, no Pardiso), dual-channel Ryzen/EPYC 4004 boxes, Hetzner Cloud US, Railway, Fly.io, small AWS hpc7a sizes, and MPI or GPU rewrites.

## Conclusion

The research reframes the question from "which machine is fastest" to "how many variants per dollar". Hardware alone buys a single-digit speedup that is capped by serial Python and by a problem too small to use many cores, while cloud cores are cheap enough that an entire 250-iteration optimization costs less than a dollar. The scarce resources are therefore engineering ones: a resumable optimizer, a launcher that fans out variants, and a measured thread-scaling curve. Those three pieces also carry forward unchanged to the order-3, multi-million-element problem, where the decisive change is algorithmic (iterative BDDC-CG replacing direct factorization as memory grows as N^(4/3)) and where larger-memory nodes and whole HPC nodes finally earn their price.

The largest unknowns are all cheap to resolve and should be resolved before committing: NGSolve's actual thread scaling for HCurl assembly, BDDC setup and sparsecholesky on EPYC; whether Pardiso under the current wheel cooperates with TaskManager; real spot interruption rates in us-east-2 and eastus2; and the Massachusetts tax treatment on the first invoice. A local alternative also deserves a benchmark before paying for anything monthly: the macOS universal2 wheel runs natively on Apple silicon with Accelerate Sparse, and M4 Max/M3 Ultra machines advertise 546-819 GB/s of memory bandwidth ([Notebookcheck](https://www.notebookcheck.net/Mac-Studio-unveiled-with-refreshed-with-Apple-M4-Max-and-Apple-M3-Ultra-SoC.973066.0.html)), though without Pardiso and with no measured NGSolve numbers.
